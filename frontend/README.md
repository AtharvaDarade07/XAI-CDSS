# Frontend

React 18, Vite, TypeScript, React Router, and Axios power the frontend. The frontend is an academic research prototype and does not establish clinical validity.

## Local development

From the project root, start FastAPI:

```powershell
..\.venv\Scripts\python.exe -m uvicorn backend.app.main:app --reload
```

In another terminal:

```powershell
cd frontend
npm install
npm run dev
```

The Axios client reads `VITE_API_BASE_URL` and defaults to `http://127.0.0.1:8000`. Copy `.env.example` to `.env.local` to override it. Local CORS is limited to `http://127.0.0.1:5173` and `http://localhost:5173`; deployment origins are not configured.

## Authentication

The login form sends username/password JSON to `POST /auth/login`, stores the returned bearer token in localStorage, then calls `GET /auth/me`. A valid token restores the user on page load. A 401 clears the token and the protected routes return to `/login`. Logout clears browser storage.

This localStorage approach is for the academic prototype: tokens can be stolen by successful cross-site scripting. Production deployment should consider stronger server-managed sessions or secure, HttpOnly, SameSite cookies, plus appropriate XSS protections. Never use real credentials in this prototype.

## Patient management

The authenticated patient workspace uses the existing FastAPI routes:

- `GET /patients?skip=…&limit=…` and `POST /patients`
- `GET /patients/{patient_id}`
- `GET /patients/{patient_id}/records?skip=…&limit=…` and `POST /patients/{patient_id}/records`
- `GET /patients/{patient_id}/records/{record_id}`

Patient listing uses the backend's offset pagination. The backend does not provide patient-code search, so the UI does not send an unsupported search parameter. Patient records display the values as stored; form bounds match the current PIMA project schema and are not universal clinical reference ranges. New patient and record forms use synthetic/project-level data only.

## Dashboard

The authenticated dashboard uses `GET /patients` for the API-reported total and a small first-page patient list, linking into the existing patient workflow. Its Add Patient action opens the existing patient-code form. It does not report prediction or record activity because no corresponding aggregate/history endpoint is available. Model version details are shown with individual predictions.

## Prediction

From a stored record's detail page, an authenticated admin or clinician can explicitly request `POST /patients/{patient_id}/records/{record_id}/predict`. The API uses the stored record and returns the prediction ID, patient and record IDs, model version, predicted class, positive-class probability, and creation timestamp. The page displays only the latest response held in the current view; the backend creates a separate prediction for every request, and no prediction-history endpoint is currently available. The probability is an experimental raw model output, not an established clinical risk estimate. No diagnosis or treatment recommendation is produced.

## SHAP explanation

After explicitly running a prediction, the record page can request `POST /patients/{patient_id}/records/{record_id}/predictions/{prediction_id}/explanation/shap`. The backend creates and persists the explanation; the frontend does not calculate SHAP. It displays the ranked feature values and contributions returned by the API. Contributions remain in the backend's raw tree-model output space and are not percentages or clinical effect sizes. Positive and negative directions describe model behavior, not clinical causation. The baseline value, when returned, is labeled as a baseline model output. Explanations are not a standalone diagnosis or treatment recommendation and require qualified human review.

## LIME explanation

After running a prediction, the record page can explicitly request `POST /patients/{patient_id}/records/{record_id}/predictions/{prediction_id}/explanation/lime`. LIME is generated by the backend as a local surrogate explanation for the same prediction displayed on the page. The UI displays the returned feature values, contribution weights, directions, output space, and configuration when present. Contribution weights are local explanation units and are not probability percentages or percentage-point changes. SHAP and LIME appear as separate explanation methods; the available consistency analysis compares them for that prediction instance. These methods describe model behavior, not clinical causation, and do not produce diagnoses or treatment recommendations. Qualified clinician review remains necessary.

## Explanation consistency

For the currently displayed prediction, the record page can explicitly request `GET /patients/{patient_id}/records/{record_id}/predictions/{prediction_id}/explanation/consistency`. The backend calculates feature overlap, Spearman rank correlation and direction agreement; the frontend only presents the returned metrics. Agreement is limited to that explanation instance and does not establish clinical validity, diagnostic accuracy, or general model reliability.
